# 全项目业务覆盖矩阵完整治理流程

## 目标

全项目业务覆盖矩阵用于证明一项生产能力能够从真实入口到达，并且存在对应实现、自动化验证和确认文档。它不是人工填写的功能愿望表，也不替代任务、会话或运行数据。

权威数据流：

```text
结构化业务清单
→ 扫描真实页面、API、CLI、确认文档和专项测试
→ 唯一业务域归属校验
→ 自动生成可读矩阵
→ 文档、测试和发布流水线共同执行门禁
```

## 唯一事实来源

- `scripts/project-coverage-manifest.json` 是覆盖关系的唯一事实来源。
- `PROJECT-COVERAGE-MATRIX.md` 由生成器确定性生成，禁止手工维护表格。
- 每个业务域保存稳定ID、状态、页面、后端根目录、生产入口、API、CLI、测试域、关键测试和确认文档。
- 页面、API、CLI和确认文档必须存在唯一主归属；共享模块只通过 `sharedBy` 引用。
- 已退役或仅为旧客户端保留的入口进入兼容区，不计入现行业务能力。

## 自动发现与门禁

覆盖审计从当前源码发现以下事实：

1. `App.vue` 中注册并展示的全部生产Tab及其真实组件。
2. 后端生产路由条件中注册的公开API前缀。
3. `ccm` 帮助与分派器公开的CLI命令。
4. 两个确认文档目录中的全部正式文档。
5. `test-domains.json` 中的领域测试、专项测试和有明确原因的辅助脚本。
6. `backend` 下全部一级生产目录。

审计会拒绝失效路径、大小写漂移、重复归属、孤立文档、未登记入口、关键测试未进入声明测试域以及生成文档被手工修改。

## 测试目录

- 正式目录识别 `selftest`、`audit`、`regression`、`e2e`、`soak`、`acceptance`、`production` 和发布证明脚本。
- 能独立验证业务的脚本必须进入正式测试域。
- Runner、子进程夹具和发布辅助脚本必须进入带原因的helper清单。
- 旧测试别名继续兼容，但不能掩盖新脚本未被任何测试或helper目录登记的问题。

## 发布流程

```text
npm run coverage:check
→ npm run docs:check
→ npm run test:all
→ npm run build
→ 生成发布候选产物
```

- Pull Request修改源码、脚本、文档、包配置或发布工作流时都会触发覆盖治理任务。
- 发布候选必须通过覆盖审计、完整领域测试、文档检查和生产构建。
- 审计回执写入 `scratch/project-coverage-audit-receipt.json`，只记录数量、覆盖率、checksum和错误，不保存源码正文或凭据。

## 兼容与删除

- 只有静态引用、动态导入、页面注册和生产构建均能证明不可达的旧组件才允许删除。
- 无法证明是否仍被外部客户端使用的旧API保留在兼容区，并明确状态和保留原因。
- 删除旧代码不会删除会话、任务、项目、记忆或用户配置数据。

## 验收

- 当前20个生产页面、后端公开API前缀、CCM CLI命令及两类确认文档覆盖率均为100%。
- 新增未登记页面、API、CLI、文档或测试时审计会失败。
- 覆盖矩阵可在Windows和Linux使用相同路径规则确定性生成。
- Provider调用为0。
