# 自动开发任务完整业务流程

确认日期：2026-07-28  
实现状态：已进入生产代码并通过任务域、Agent域、真实任务链和生产构建验证

## 业务目标

用户只需要提供业务描述、图片、附件或公开文档，CCM负责识别需求、选择执行位置、读取真实源码、制定计划、创建任务、排队开发、独立验收、返工和最终交付。全局 Agent、任务派发、我的工作台、群聊会话和项目会话不会各自维护一套临时流程，而是进入同一套持久任务、执行队列、权限、TestAgent、任务回放和记忆准入链路。

```text
用户需求、图片、附件或公开文档
→ 统一模型判断普通问答或业务任务
→ 确认执行群聊/项目及精确会话
→ 解析资料并形成目标、范围和验收标准
→ 主 Agent读取真实源码并制定计划
→ 创建Epic、工作项和依赖关系
→ 进入精确会话串行队列
→ 项目开发 Agent按工作项实现
→ TestAgent独立验收或主 Agent自验
→ 失败则生成精确返工单并复验
→ 主 Agent最终验收
→ 低风险自动完成或等待用户批准
→ 回传原始会话、生成任务回放并准入长期记忆
```

普通问答直接由相应主 Agent回答，不创建开发任务、队列记录或任务回放。模型不可用、资料未读、源码证据不足、作用域不匹配或权限未通过时停止执行，不使用关键词规则伪造计划。

模型与运行时异常采用统一分级重试和中断恢复链。普通问答不会进入长任务的六分钟预算；开发任务重试耗尽后停止当前执行并保留任务、计划、源码现场和子Agent原生会话。用户可以恢复同一任务，永久取消则保持终态但仍保留回放。完整规则见[分级重试、任务中断与会话恢复](./TASK-INTERRUPTION-AND-RECOVERY.md)。

## 用户入口

### 全局 Agent

全局 Agent先判断消息是普通问答还是业务需求。业务需求可以被拆成一个全局 Mission和多个下游任务，然后根据模型确认的执行位置派发给群聊主 Agent或项目主 Agent。

全局 Agent负责确定执行位置、拆分和监督任务、聚合下游结果，不直接修改项目源码，也不代替下游主 Agent调用TestAgent。来自Web的任务只回复Web会话；来自飞书的任务只回复原飞书会话。

### 任务派发

用户选择群聊或项目及其精确会话，填写需求并上传资料。模型先生成可编辑的任务图；用户确认后，系统原子创建父任务、子任务、依赖和队列记录。一个文档可以拆成多个顺序任务，依赖未完成的任务不能提前执行。

需求池条目或资料摄取草稿创建时即保存目标scope、目标群聊/项目和精确会话。之后即使用户切换页面中的活动会话，确认、手动派发、批量派发和定时认领仍默认进入创建时保存的会话。用户可以在确认卡或需求池卡片中明确改选同一群聊/项目下的可写会话；服务端重新核验后才更新目标。原会话被归档或删除时任务进入阻塞并要求改选，绝不隐式跟随新的活动会话。历史未保存会话的条目只在首次认领或派发时惰性固定一次，不批量改写历史。

### 我的工作台

用户先选择目标群聊或项目及其精确会话，再提交业务描述和资料。工作台复用任务派发的需求解析、任务图确认和持久任务接口，不创建独立的工作台任务数据库。未明确选择现有会话时，服务端为本次需求创建专属自动化任务会话；预览、确认、正式任务、队列、回放和最终回复始终沿用该会话。

### 群聊会话

当前群聊主 Agent接收需求。它可以读取群聊管理的多个项目源码，识别影响项目，形成跨项目计划，并把每个工作项交给对应项目子 Agent。跨项目依赖仍由群聊主 Agent统一协调。

### 项目会话

当前项目主 Agent接收需求。它只能读取当前项目和当前精确项目会话，只能把工作项交给该项目配置的唯一开发 Agent，不能访问兄弟项目、群聊上下文或伪造群聊任务。

### 会话列表分类

- 群聊页面把会话分为“普通会话”和“自动化任务会话”。普通会话承载用户直接对话；自动化任务会话承载需求池、任务派发、工作台和自动调度创建的持久任务。
- 项目页面在上述两类之外继续独立展示“飞书会话”。飞书会话只接收绑定飞书来源的项目主 Agent消息，不作为Web工作台或Web任务派发的默认目标。
- 分类只是会话列表投影，不建立第二套消息或任务存储。旧会话没有类型字段时，服务端根据其绑定的正式任务惰性识别；新自动化任务会话创建时直接保存`session_kind=automation`。
- 用户明确选择普通会话时，自动化任务可以绑定该会话；未选择时创建新的自动化任务会话。任何入口都不能使用后来切换的活动会话覆盖已保存目标。

## 角色与责任

| 角色 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 全局 Agent | 识别业务需求、确定执行位置、创建Mission、派发和汇总下游交付 | 修改源码、直接管理项目子 Agent、替代TestAgent验收 |
| 群聊主 Agent | 读取群聊管理项目的源码、跨项目规划、创建工作项、权限仲裁、协调子 Agent、最终验收 | 亲自修改业务源码 |
| 项目主 Agent | 读取当前项目源码、项目内规划、派发唯一开发 Agent、权限与最终验收 | 访问兄弟项目或群聊上下文 |
| 项目开发 Agent | 在正式工作项和允许路径内修改源码、运行验证并提交结构化回执 | 自行扩大范围、批准高风险权限、宣布最终交付 |
| TestAgent | 根据目标、验收标准、真实变更和测试目标进行独立只读验收 | 修改代码、替代主 Agent派发或最终决策 |
| 用户 | 提供目标和资料，处理业务方向、高风险权限与必要的最终批准 | 理解内部任务ID、Provider或原生session协议 |

## 完整执行阶段

### 1. 接收与资料解析

系统保存用户原始描述、消息来源、附件引用和精确目标会话。图片、附件和公开在线文档先由统一资料接入链读取，再把解析结果交给模型。任务标题和聊天正文保留用户原始表达，不把整份文档重复写进聊天。

每份资料记录已读取、部分读取、需要授权、格式不支持或读取失败。写入型任务的必需资料未完整读取时进入等待补充状态；用户重新上传或授权后可以继续原任务，不能新建一个没有原上下文的任务绕过门禁。

### 2. 模型识别与任务身份

统一模型判断：

- 普通问答：直接回复，不创建任务。
- 只读分析：主 Agent可使用当前作用域授权的只读源码、MCP、Skill、知识库和共享文件。
- 明确开发任务：进入计划和执行链。
- 复杂、高风险或信息不足任务：先展示计划或待确认问题。

每次正式提交生成 `TaskIntakeIdentityV2`，绑定来源渠道、目标scope、目标ID、精确会话、客户端消息ID、内容checksum和工作流类型。同一次网络重试返回原任务；用户再次提交相同需求会创建新任务；相同文字发往其他群聊、项目或会话不会串任务。

### 3. 主 Agent读取源码并制定计划

群聊主 Agent先读取所管理项目的结构，项目主 Agent只读取当前项目结构。模型最多进行三轮只读检索，选择目录、文件、定义、引用和配置证据。服务端拒绝敏感文件、依赖目录、构建产物、目录越界和符号链接逃逸。

计划包含：

- 用户目标与明确的非目标。
- 影响项目、模块和文件证据。
- 数据关系、接口关系和跨项目依赖。
- 可执行工作项及先后顺序。
- 每个工作项的允许路径和验收标准。
- 未确认事项、权限要求和风险等级。

源码证据保存相对路径、文件checksum和整体快照checksum，不把源码正文堆到任务卡。执行前再次核验源码快照；源码变化后旧计划失效，主 Agent必须更新计划或重新请求确认。

### 4. 创建任务图

简单开发需求创建一个正式工作项。复杂需求创建Epic和多个子工作项，保存父子关系、依赖图、执行项目、验收标准、精确会话和来源任务。

群聊任务可以包含多个项目工作项；项目任务的所有工作项始终绑定当前项目。模型生成的计划需要用户确认时，确认前不会启动开发 Agent。任务创建、计划、用户确认和后续执行都沿用同一个任务身份。

复杂需求中的每个工作项保存各自目标的精确会话，而不是继承一个可能属于其他群聊或项目的父任务会话。创建子任务前服务端再次校验目标项目、群聊成员关系和会话归属；跨目标、失效或越界会话均停止派发。

### 5. 进入精确会话队列

队列按精确 `group_id + group_session_id` 或 `project_id + project_session_id` 隔离。同一精确会话一次只执行一个普通开发任务，不同会话可以并行。

- 普通任务按入队顺序执行。
- 插队任务移动到等待队列前部，但不打断正在运行的任务。
- Epic依赖优先于插队；前置工作项未验收时，后继项不能启动。
- 当前任务进入完成、失败、阻塞或取消终态后才释放队首。
- 等待用户的任务进入明确阻塞状态并释放队首，补充信息后重新按优先级入队。

### 6. 项目开发 Agent执行

主 Agent生成自包含工作单，包含目标、源码证据、允许路径、依赖结果、验收标准、当前任务记忆和必要工具。开发 Agent通过签名MCP读取绑定的精确会话、当前任务和相关项目长期记忆，不能读取兄弟会话或其他项目。

开发 Agent原始输出、工具过程、文件变化和验证命令进入任务时间线与任务回放，不直接成为用户聊天气泡。进程退出码为0只代表执行结束，不能把任务标记为已完成。

当群聊中的项目子 Agent A需要项目B配合时，A只能通过 `ccm__group_coordinator` 向群聊主 Agent提交协调请求。群聊主 Agent核验后为B创建独立工作项、worktree和原生Agent会话；B的结果通过持久任务和验收链返回主 Agent，再恢复A的原任务会话。子 Agent之间不直接互发命令。

### 7. 权限处理

读取项目目录、搜索和读取普通源码默认允许。项目内低风险操作可以按现有策略由主 Agent批准；高风险、破坏性、发布部署、越界访问、凭据和用户确认型操作必须回到当前精确会话请求用户。

飞书来源的权限请求回到原飞书会话，Web来源只显示在原Web会话。等待权限时任务不会后台无限重试，也不会错误展示为完成。

### 8. TestAgent独立验收与返工

文件或代码发生变化后，默认进入TestAgent。TestAgent只读取用户目标、验收标准、实际变更、开发回执、验证命令、项目测试目标和完成验收所需的证据，不读取无关项目或群聊。

- 通过：结果交给主 Agent做最终验收，不能直接完成任务。
- 实现问题：主 Agent根据失败证据生成精确返工单，交回原开发 Agent，并尽量复用原native session。
- 环境或凭据问题：进入阻塞并告诉用户需要处理什么，不把环境问题伪装成代码失败。
- 最多返工三轮；仍未通过时进入 `blocked`。

用户关闭全局TestAgent开关后，不运行独立TestAgent，由对应群聊或项目主 Agent只执行一轮自验。页面和回放必须明确标记“主 Agent自验，非独立验收”，证据不足时仍不能交付。

### 9. 主 Agent最终验收

主 Agent核对全部工作项、真实文件变化、验证结果、TestAgent结论、权限、阻塞项、源码快照和交付范围。只有证据一致时任务才能进入完成流程。

低风险、全部子任务通过、没有待审批权限、没有发布动作、源码证据完整且模型未要求确认的Epic可以自动验收。中高风险、发布部署、破坏性操作、跨项目越界、证据不足或用户明确要求确认时等待用户批准。自动验收和用户批准复用同一个完成函数。

终态统一为：

| 任务结果 | 任务状态 | 验收状态 |
| --- | --- | --- |
| 交付通过 | `done` | `accepted` |
| 执行失败 | `failed` | `rejected` |
| 等待用户或无法继续 | `blocked` | `blocked` |
| 用户取消 | `cancelled` | `cancelled` |

每个终态生成 `TaskTerminalStateReceiptV1`；Epic最终验收生成 `EpicAcceptanceDecisionV1`。任务列表、详情、回放、飞书通知和长期记忆准入读取同一份规范化结果。

### 10. 回传、任务回放与记忆

最终回复包含完成内容、变更文件、真实验证、是否发布、风险和未完成事项。结果只回到原始来源会话：Web不会串到飞书，飞书不会串到其他飞书或Web会话。飞书只直接进入全局Agent或项目主Agent；群聊处理全局飞书下游任务时沿原全局来源回执返回，不建立独立群聊飞书会话。

任务回放以父任务为根聚合：

- 原始需求、来源和资料读取状态。
- 模型计划、源码证据和计划变更。
- 父子工作项、依赖、队列、插队和恢复记录。
- 开发Agent执行、文件变化和验证命令。
- TestAgent计划、报告、截图和每轮返工。
- 权限请求、用户补充、最终验收和终态回执。

用户聊天区只展示主 Agent的正式消息。Provider、generation、native session、MCP、Skill、原始协议和内部错误栈放在二次展开的排障信息中。

只有最终验收通过后的决定、稳定约束、结论和仍未完成事项可以成为长期记忆候选。失败文本、返工过程、普通工具日志和未验收的开发输出不会直接写入正式长期记忆。

## 用户实时看到什么

同一个任务身份持续更新一张用户可理解的任务卡：需求确认、资料读取、计划、队列位置、当前执行成员、开发进度、独立验收、返工轮次、用户介入和最终交付。任务卡中的“已派发”只表示已经进入队列，不代表开发完成。

全局 Agent显示“确定执行位置、拆分、派发、跟踪下游和汇总交付”；群聊与项目主 Agent显示“理解需求、制定计划、开发执行、独立验收、返工、最终验收”。因此页面外观和完成口径统一，但不会把全局 Agent显示成亲自修改源码。

### 计划书的持久化、修订与恢复

三类 Agent共用同一套计划摘要卡和一级任务详情，但角色文案不同。摘要只展示目标、当前阶段、当前步骤、下一步和真实进度；一级详情通过 `GET /api/tasks/replay?task_id=<id>` 惰性读取完整模型计划、影响范围、源码依据、全部步骤、验收标准和修订历史。超过20步的计划不截断，步骤区独立滚动并优先显示当前、失败、返工或待确认步骤。完整计划读取失败时仍保留任务卡中的持久预览，并明确说明无法读取，不能用通用阶段冒充原计划。

项目任务创建后，服务端立即在精确项目会话 upsert 稳定消息 `project-main-task:<task_id>`。计划、开发、验收、返工、阻塞和终态都更新这一条权威消息；浏览器不再另存一条助手任务消息。项目运行事件携带同一个 `message_id`，页面刷新、SSE断线或切换会话后，通过精确项目、会话和任务身份重新水合，因此后台任务不会随浏览器连接终止，也不会出现重复任务气泡。Web与飞书使用同一任务投影，但最终回复仍只回到原来源。

等待确认且尚未开始源码执行的项目计划，可以通过“补充要求”在同一任务内修订。修订请求绑定 `client_message_id`，重复提交不会再次调用模型。项目主 Agent重新读取当前源码并生成新计划，只有新计划通过结构和源码证据校验后才原子替换工作项、验收标准和源码checksum；失败时保留上一版有效计划。任务ID、父运行ID、队列身份和开发Agent会话均不变化，旧计划作为 `ProjectMainPlanRevisionV1` 永久进入回放。开发已经开始后的目标变化使用同任务停止当前轮、重新规划和复验流程。

验收角色在任务创建时固化：TestAgent开启时显示“TestAgent（独立验收）”，关闭时只显示“主 Agent自验”。摘要、详情、返工、轮次、最终交付和任务回放读取同一 `acceptance_mode`，不能在关闭独立验收后仍声称经过TestAgent。全局任务只描述对下游验收的跟踪和汇总，不把下游开发或TestAgent展示成全局Agent亲自执行。

## 异常恢复与防循环

- 队列处理器使用最外层 `try/finally` 清理运行标记。
- Fire-and-forget启动异常会写入时间线，并只安排有限次数的队列唤醒。
- 租约连续失败最多恢复三次，之后进入阻塞，不无限抢占。
- Provider调用遵守统一超时、最多五次请求重试和任务级冷却；确定性错误不重试。
- TestAgent返工最多三轮，同一失败证据不会反复创建兄弟任务。
- 服务重启从持久任务、租约、队列和Agent会话状态恢复；无法证明归属时先关闭旧租约，不误杀未知进程。
- 状态、通知或回调异常不能让任务永久保留为游离的 `in_progress`。

## 七项生产保障

1. `TaskIntakeIdentityV2`保证精确作用域幂等，不按需求文字跨请求去重。
2. 精确会话严格串行，插队不打断当前工作，阻塞会释放队首。
3. 队列异常必清理运行标记，并提供有上限的持久恢复。
4. 源码规划由模型基于真实只读证据完成，不用关键词规则替代语义判断。
5. 低风险自动验收与中高风险人工批准使用统一门禁和完成函数。
6. 终态、验收状态、时间线、通知、回放与长期记忆准入读取统一结果。
7. 真实任务链测试使用独立目录、数据库和端口，检查未处理Promise、租约泄漏、重复执行与状态不一致。

统一任务系统的身份结构、双层串行、终态门禁、兼容入口和故障恢复细节，见 [自动开发统一任务系统V2](./AUTOMATIC-DEVELOPMENT-UNIFIED-TASK-SYSTEM-V2.md)。
