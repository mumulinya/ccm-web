# 飞书消息进入 ACP 前阻塞修复

## 问题边界

飞书消息到达 `cc-connect` 后，旧运行配置会先同步调用飞书表情接口添加 `OnIt`。该 SDK 请求没有超时；网络异常时会阻塞在 `StartTyping`，消息因此无法进入 CCM ACP，也不会启动模型五次重试和 190 秒 ACP 超时。

真实日志中的特征是：已记录 `processing message` 和飞书表情创建成功，但之后没有 `session/prompt`、模型请求或超时回复。

## 修复

- 全局飞书控制机器人生成配置固定写入 `reaction_emoji = "none"`。
- 新建和编辑的项目飞书配置同样关闭同步表情。
- 已有项目启动时只规范化私有运行配置，不修改用户保存的 TOML。
- 全局和项目飞书 ACP 运行配置使用 `reset_on_idle_mins = 0`，不再向用户展示内部会话轮换提示。
- ACP 收到 `session/prompt` 时立即记录模式、会话、请求 ID、文本长度和不支持的附件数量，不记录消息正文。
- 模型层原有五次重试、单次 30 秒和总计 180 秒预算继续生效。
- `cc-connect` 自带的同步表情仍保持关闭；CCM 在 ACP 已经接收消息后，通过独立的本机内部接口异步添加 `OnIt`。
- 全局和项目通道都从当前 ACP 会话绑定的 `feishu:...:root:om_*` 精确解析消息 ID，不按“最近消息”猜测，也不允许跨会话指定消息。
- 主 Agent 的最终可见回复成功写入 ACP 后，CCM 异步移除 `OnIt` 并添加 `Done`。
- 超时、失败和取消只移除 `OnIt`，不添加 `Done`；表情 API 自身失败不会改变主 Agent 的执行结果或阻塞飞书回复。
- 单次 Token、添加和删除表情请求均有 2 秒硬超时，活动状态另有 15 分钟兜底清理。

CCM 的表情、卡片和最终回复共同提供处理反馈；表情提示只是旁路反馈，不再作为消息处理链的前置依赖。

## 验证要求

- Feishu 与 Lark 私有运行配置必须包含 `reaction_emoji = "none"`。
- 其他平台的表情配置不能被修改。
- 规范化必须幂等，用户保存的项目配置保持不变。
- 日志出现 `prompt received` 后，后续失败归入 ACP 或模型阶段；没有该日志则属于 `cc-connect` 或平台前置阶段。
- 同一个消息的重复开始通知只能创建一个 `OnIt`。
- 成功顺序必须是 `OnIt -> 删除 OnIt -> Done`。
- 失败顺序必须是 `OnIt -> 删除 OnIt`，不得出现 `Done`。
- 内部反馈接口只允许回环地址且必须携带 `X-CCM-ACP: 1`。
