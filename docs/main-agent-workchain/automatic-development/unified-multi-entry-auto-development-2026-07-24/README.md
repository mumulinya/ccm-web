# 全入口自动开发与会话队列

## 目标

用户可以只提供业务描述、图片或文档，让 CCM 完成需求理解、模型拆分、任务排队、开发执行、独立验收、返工和最终总结。任务派发、工作台、全局 Agent、群聊会话和项目会话共用持久任务、执行队列与任务回放，不再形成互相独立的临时流程。

## 四个入口

1. **任务派发**：选择群聊或项目及其精确会话，上传资料并生成任务图。模型可拆成多个持久任务，用户确认后自动入队。
2. **全局 Agent**：普通问答直接回答；业务需求由模型形成全局 Mission，并向目标群聊或项目创建持久子任务。
3. **我的工作台**：选择指定群聊或项目，提交目标和资料。工作台调用与任务派发相同的需求摄取、确认与 Epic 创建接口。
4. **群聊/项目会话**：主 Agent先用模型判断是否需要执行。普通询问不创建任务；开发需求进入当前精确会话的任务链。

## 统一数据流

```text
用户文字 / 图片 / 文档
-> 模型需求提取与工作流判断
-> 执行前计划或 Epic 任务图
-> 用户确认（高风险、复杂或信息不足）
-> 持久父任务与分派子任务
-> 精确会话串行队列
-> 群聊主 Agent 或项目主 Agent
-> 第三方开发 Agent
-> TestAgent 独立验收
-> 失败证据生成返工单并重新排队（最多三轮）
-> 主 Agent 最终验收
-> 任务回放聚合全部证据
```

模型是语义决策来源。文件解析器只提取可供模型阅读的内容，不用关键词或正则替代任务/问答、拆分数量、项目选择和验收决策。模型不可用时 fail closed，不创建伪任务图。

## 会话队列

- `queue_scope=conversation_serial` 时，队列键绑定精确 `group + gcs_*` 或 `project + project session`。
- 同一会话的多个分派任务每次只运行一个；上一任务完成、失败、阻塞或取消后才处理下一项。
- 不同会话可以并行，避免一个项目的独立会话互相阻塞。
- 普通优先级按入队顺序执行；高优先级插入当前会话等待队列前部，但不会强制杀死已经运行的任务。
- 已经排队的任务点击“插队”会真实移出并重新插入队列，同时记录 `task_queue_reprioritized` 时间线事件。
- Epic 依赖仍优先于队列优先级：依赖未验收通过的子任务不能靠插队绕过。

## 项目验收

项目直派任务不再因为要求独立复核而拒绝执行。开发 Agent返回后由项目独立 TestAgent读取当前源码、实际变更、开发回执和项目测试目标：

- 验收通过后才允许任务进入完成状态。
- 验收失败会保存报告和证据，并生成精确返工要求。
- 返工任务重新进入同一会话队列，继续复用同一任务与第三方 Agent原生会话。
- 最多三轮；仍失败则进入 `blocked`，不伪造完成结果。

## 任务回放

任务派发列表每个任务都有“任务回放”入口。回放以父任务为根聚合：

- 原始需求来源、附件摄取和模型计划。
- 父子任务、依赖、队列和插队记录。
- 群聊主 Agent、项目主 Agent和开发 Agent执行时间线。
- 文件变更、命令验证、TestAgent计划、报告、截图和产物。
- 每轮返工、最终验收、阻塞原因和用户补充。

原始执行记录不会因为自动开发流程升级而删除；旧任务继续按已有 task ID 回放。

从任务派发、工作台或全局 Agent指定项目后，系统会创建或绑定精确项目会话，并把用户目标与项目主 Agent的正式排队确认写入该会话。开发 Agent原始输出、TestAgent内部报告和返工过程只进入任务时间线与任务回放，不直接塞进聊天正文。

## 接口与状态

- 统一预览：`POST /api/usability/intake/preview`
- 确认并原子创建任务图：`POST /api/usability/intake/confirm`
- 任务排队：`POST /api/tasks/queue`
- 队列批量操作：`POST /api/tasks/queue-batch`
- 优先级与插队：`POST /api/tasks/update`
- 完整回放：`GET /api/tasks/replay?task_id=<id>`

任务新增或统一使用：`request_origin`、`origin_session_id`、`orchestration_scope`、`group_session_id`、`project_session_id`、`queue_scope`、`review_round` 和 `acceptance_state`。
