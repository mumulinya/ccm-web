# 全局 Agent 业务任务用户旅程

## 目标

用户从全局 Agent 提交一段业务描述、图片、附件或在线文档后，应始终能回答六个问题：

1. 系统理解的目标是什么。
2. 哪些项目或群聊负责执行。
3. 上传资料是否真的读取成功。
4. 当前在排队、开发、验收、返工还是等待用户。
5. 任务失败或暂停后需要处理什么。
6. 最终完成了什么、验证了什么、是否实际发布。

普通问答继续直接回复，不创建任务卡和任务回放。

## 权威流程

```text
用户原始需求
-> 模型工作流决策
-> 需求确认与资料读取覆盖
-> 全局 Agent 创建或派发任务
-> 精确会话串行队列
-> 群聊/项目主 Agent 执行
-> TestAgent 独立验收
-> 失败范围定向返工并复验
-> 主 Agent 最终验收
-> 同一任务卡输出交付报告
```

上传资料的解析上下文只作为模型输入和验收依据，任务标题、聊天正文和推理目标保留用户原始描述，避免把整份文档内容重复写进聊天界面。

## 用户可见信息

全局、群聊和项目任务复用同一套 `TaskExperienceCard`：

- **需求确认**：用户目标、执行范围、负责项目、验收标准和待澄清问题。
- **资料覆盖**：逐份显示已读取、部分读取、需要授权、格式不支持或读取失败。
- **队列状态**：显示真实队列位置、前置依赖和当前执行成员。
- **实时阶段**：理解需求、制定计划、开发执行、独立验收、返工、最终验收和完成交付。
- **用户介入**：原因、要执行的动作及暂停期间的影响。
- **返工信息**：当前轮次、最大轮次和本轮失败范围。
- **最终交付**：完成内容、修改文件、真实验证、发布状态、风险和遗留项。

默认界面只保留一张持续更新的任务卡。工具事件、Provider、session、generation、MCP、Skill 和原始协议数据继续保留在技术详情或任务回放中。

### 角色化阶段

共用任务卡只统一外观、状态颜色、资料覆盖、用户介入和交付报告，不混淆主 Agent 职责：

- 项目主 Agent 与群聊主 Agent：`理解需求 -> 制定计划 -> 开发执行 -> TestAgent（独立验收） -> 最终验收 -> 完成交付`。
- 全局 Agent：`理解需求 -> 确定执行位置 -> 创建或拆分任务 -> 派发与排队 -> 跟踪下游 -> 汇总交付`。

全局任务的通用 `executing/reviewing/reworking` 状态分别投影为“跟踪下游执行、汇总下游验收、下游任务返工”，不得显示为全局 Agent 亲自开发源码或亲自运行 TestAgent。下游 TestAgent 证据可以进入全局最终汇总，但只表述为对下游验收结果的核对。

## 资料执行门禁

- 只读分析可以说明资料读取失败，但不得猜测文件正文。
- 写入和高风险工具执行前检查全部必需资料。
- 必需资料未完整读取时，原运行进入 `waiting_clarification`，保留步骤、进度和证据。
- 用户完成授权、重新上传后可继续原运行。
- 用户明确知情并允许忽略未读资料时，由模型返回 `sourcePolicy=ignore_unread`；豁免只绑定当前运行。
- 不允许通过本地关键词、字符截断或新建无上下文任务绕过门禁。

## Web 与飞书

- Web 和飞书使用相同任务状态和完成口径。
- 飞书运行事件与最终回复绑定同一 `cardKey`、run 和 mission，阶段更新同一任务卡。
- “已派发”只表示进入自动执行链路，不表示开发完成。
- 等待确认时用户可直接回复“确认”或“取消”，默认消息不暴露内部运行 ID。
- 飞书来源的最终结果只回原飞书会话；Web 来源不会被转发到飞书。

## 完成口径

- Agent 进程退出、工具调用成功或任务创建成功都不是最终完成。
- 文件修改任务必须有实际变更和真实验证结果。
- 需要独立验收的任务必须经过 TestAgent，并由主 Agent 完成最终验收。
- 返工只覆盖失败范围，同时保留必要回归项。
- 未记录部署或发布证据时，报告明确写明“不能视为已经上线”。

- `npm run check`
- `npm run build:frontend`
- `npm run build:backend`
- `node scripts/task-user-runtime-ux-selftest.mjs`
- `npm run test:tasks`
- `npm run test:agents`

所有验证均使用本地自检或 mock Provider，不产生付费模型调用。
